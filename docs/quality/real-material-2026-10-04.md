# 実素材によるHD出力・改訂の検証 — 2026-10-04

## 結論

既存のGenie実演動画を読み込み、構成確認、編集・保存、横長/縦長HD書き出し、
ZIP取得、同じ素材での改訂、保存状態の再読込を実行した。
この過程で、**冒頭の見出し・補足を編集してもMP4へ反映されない不具合**を再現した。
編集済みのhookを読むよう修正し、同じ素材・同じ保存済み構成で再検証した。

字幕欄は別ファイル `captions.srt` の文言であり、MP4へ焼き込まれない。
「見出し・字幕の編集は映像に反映」という日英の案内も訂正した。
新しい字幕焼き込み機能は追加していない。

## 対象と素材

- 検証開始時のmain: `c4d637b73cb80e36a1aaef2bfb09d48993db5c62`
- 素材: [既存のGenie実演](https://reachmade.com/media/originals/genie/assets/genie-orbit-web.mp4)
- 素材を保持する所有者のリポジトリ: `FORIFOR/reachmade`、`1e4bee47f4d268d6f3c33e0ff58e1021945dc2f0`
- 素材Git blob: `0e3b999ca606a751e1e00ac28bbb85e838b0b7e8`
- 素材SHA-256: `4d4fb8d4fde5d1f7ead1ae738a29f64293dc8588fa305ebafac73c79c487c5c3`
- 既存素材33秒のうち3〜23秒を使用。新しい画面収録ではなく、既存の編集済み実演を再編集した
- 元素材にある待ち時間短縮やGenieの旧版表示を、現在のGenieの品質・速度の証明には使わない
- 音声素材を別指定していないため、今回の書き出しは無音

所有者のローカルチェックアウトにある素材のバイト列を、Git blobと既存originals manifestの
SHA-256/サイズに照合した。元素材を変更せず、合成テストパターンではない映像を使用した。
映像自体をこのPRや外部サイトへ公開していない。

## 実行方法と検証境界

Linux x86_64 / Python 3.12.14。独立venvへ宣言済み依存をインストールした。
FastAPI 0.128.8、uvicorn 0.48.0、Pydantic 2.13.5、Pillow 12.3.0、
Playwright 1.57.0、NumPy 2.5.3。`pip check`成功。

実ASGI経路、SQLite、worker、FFmpegを使い、次を実行した。

1. 事実と既存実演であることを明記した企画を作成、使用権を確認した既存動画を取り込む
2. `capture_mode=upload`、`quality=hd`、`review_plan=true`、`capture_start=3`、`capture_length=20`で作成
3. 確認待ちで字幕欄を編集して保存し、明示的にレンダリング
4. 実際のMP4を全編デコードし、ZIPと全ファイルハッシュ、字幕・LP・SNS原稿を検査
5. 冒頭見出しと字幕を変更して、同じキャンペーン・同じ映像で改訂
6. 不具合修正後、保存済み構成を変えずに再出力し、再起動後の版とZIPを照合

外部モデル、SNS、課金生成、デプロイは無効。公開操作は行っていない。
ブラウザのlocalhost制限を迂回していないため、これはブラウザの操作試験ではない。
人の初回導入・編集の所要時間も計測していない。下記秒数は機械の待機時間である。

## 修正前の失敗

初回HD書き出し164.28秒、改訂163.37秒。両方とも26秒、1920×1080および1080×1920、
H.264/30fpsで全編デコードできた。しかし、冒頭見出しを変更してもMP4は同じバイト列だった。

| 出力 | 初回と改訂で一致したSHA-256 |
|---|---|
| 横長 | `77b40298b2150b5b2036bafa0e868c420000a5315bb7ba836c4373c10dad61b9` |
| 縦長 | `d640dfbd79ec6c244fbea9d58db3a4ea7bb80d48e42c7266ad9fa559b6c8ede4` |

保存された構成の冒頭は新しい見出しになり、改訂番号も進んでいた。
原因は `render_frame()` の冒頭だけが、構成ではなく元企画のtagline/audienceを読んでいたこと。
機能紹介と最後のシーンは、すでに構成のtitle/detailを使用していた。

独立したフレーム回帰試験でも、縦横・3スタイル・見出し/補足の12条件で修正前に失敗した。
修正後は同じ条件で異なる画素を確認した。字幕だけを変えた10フレーム比較はすべて同じ画素で、
SRTが別ファイルという現在の実装も確認した。

検証側の初回コードには、最初の出力を改訂1と誤認したassertがあった。
実装は初回0、最初の改訂1が正しい。元失敗を残してこの期待値だけを訂正し、
その後も残った「MP4が変わらない」失敗を製品不具合として扱った。

## 修正後の結果

修正後は163.95秒で再出力した。21項目を確認し、保存済みの冒頭見出しが横長・縦長の
MP4へ実際に反映された。冒頭・本編・終了場面のデコード画像も目視した。
両MP4は26秒、1920×1080 / 1080×1920、H.264/30fpsのままで、全編デコード成功。
16ファイルのZIPとmanifestハッシュ、SRT、再起動後の改訂2、ダウンロードしたZIPの同一性を確認した。

全スイート、ブラウザUI、画像比較CIの成功へは読み替えない。

## 文言同期と残る制限

- 標準スタジオの見出し・補足は、生成した映像レイアウトに反映される
- 字幕欄はSRTファイル。MP4への焼き込みや、読み込んだ映像に既に入っている文字の変更は行わない
- LP/SNSは元企画を使用する。今回の改訂でもLP HTMLとSNS原稿は変更されなかった
- 今回の元企画と変更後の見出しはどちらも既存実演を指すため、確認した文章に事実上の矛盾は見つからなかった。ただし全文言が自動同期したという意味ではない
- 実ブラウザ、OS IME、スマートフォン実機、人の初回利用、外部サービス、本番公開は未検証
- 元素材の細かいUI文字の読みやすさ、表現品質、顧客の受入、販売や成果は別に評価が必要

この検証は、製品全体が完成したこと、商用SLA、独立した品質認定を意味しない。
